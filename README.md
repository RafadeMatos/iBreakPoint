# iBreakPoint

**Embedded Firmware Diagnostics & Robustness Testing**

CLI em C para diagnóstico de dispositivos seriais e comunicação com firmware próprio para Raspberry Pi Pico (RP2040). O projeto começa com uma abordagem simples: identificar dispositivos, verificar a comunicação e avaliar se o ambiente está pronto para executar os testes disponíveis.

> **iBreakPoint v0.1.0** — primeira versão pública, com foco em diagnóstico local e comunicação serial.

## Visão geral

O iBreakPoint é um projeto experimental de engenharia de software e diagnóstico de firmware embarcado, escrito em C.

A proposta é construir uma ferramenta pequena, compreensível e verificável, capaz de distinguir entre a presença de um dispositivo serial e a confirmação efetiva de comunicação com o firmware esperado.

Detectar uma porta serial não significa que o dispositivo está executando o firmware correto. Por isso, o projeto separa a enumeração do transporte da validação do protocolo.

### Funcionalidades

| Módulo | Responsabilidade |
|---|---|
| **Device** | Enumerar dispositivos seriais disponíveis e consultar informações do transporte. |
| **DocTor Who** | Inspecionar a comunicação, verificar o handshake e apresentar informações de diagnóstico. |
| **Analyze** | Avaliar ferramentas, permissões e condições necessárias para as operações disponíveis. |
| **About** | Apresentar informações sobre o projeto e sua versão. |

O escopo atual é deliberadamente limitado. O objetivo desta versão é estabelecer uma base funcional antes de adicionar recursos mais complexos de análise e robustez.

## Arquitetura

O projeto está dividido em três partes principais:

```text
iBreakPoint/
├── include/          # Interfaces públicas
├── src/              # CLI, comunicação e diagnóstico
├── firmware/         # Firmware para Raspberry Pi Pico
├── tests/            # Testes automatizados
├── docs/              # Documentação do protocolo
├── CMakeLists.txt
└── README.md
```

**Host:** aplicação CLI em C, compilada com CMake para Linux.

**Firmware:** implementação própria para Raspberry Pi Pico/RP2040, construída com o Pico SDK.

**Comunicação:** transporte serial USB CDC e protocolo textual para o handshake e as operações implementadas.

## Requisitos

### Host — Fedora Linux

Dependências de compilação:

```bash
sudo dnf install gcc gcc-c++ cmake make
```

O dispositivo físico não é necessário para compilar a aplicação do host. A validação da comunicação, porém, depende de um dispositivo compatível e acessível.

## Instalação e build

Na raiz do repositório, execute:

### 1. Configurar o projeto

```bash
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release
```

### 2. Compilar

```bash
cmake --build build --parallel
```

### 3. Executar os testes

```bash
ctest --test-dir build --output-on-failure
```

### 4. Executar a aplicação

```bash
./build/ibreakpoint
```

Para consultar as opções disponíveis:

```bash
./build/ibreakpoint --help
./build/ibreakpoint --version
```

Instalação local opcional:

```bash
sudo cmake --install build
```

> **Nota:** os comandos acima descrevem o fluxo de build previsto pelo projeto. Consulte os resultados dos testes e as limitações abaixo para distinguir validação automatizada de validação em hardware real.

## Firmware — Raspberry Pi Pico

O firmware destina-se à placa Raspberry Pi Pico baseada no RP2040.

### 1. Preparar o Pico SDK

Instale e configure o [Raspberry Pi Pico SDK](https://github.com/raspberrypi/pico-sdk) conforme a documentação oficial. Defina `PICO_SDK_PATH` para o diretório correto do SDK.

### 2. Compilar o firmware

Na raiz do repositório:

```bash
cmake -S firmware -B firmware/build -DPICO_BOARD=pico
cmake --build firmware/build --parallel
```

Se a compilação terminar com sucesso, o arquivo UF2 esperado será:

```text
firmware/build/ibreakpoint_pico.uf2
```

### 3. Gravar a placa

1. Desconecte a placa do computador.
2. Mantenha o botão **BOOTSEL** pressionado enquanto conecta o cabo USB.
3. Copie o arquivo UF2 para a unidade USB disponibilizada pela placa.
4. Aguarde a reinicialização e a enumeração do dispositivo serial.

O nome da unidade, a porta serial e o comportamento de enumeração podem variar conforme o ambiente.

### 4. Verificar a porta serial

No Linux, procure primeiro identificadores persistentes:

```bash
ls -l /dev/serial/by-id/
```

Se necessário, consulte também:

```bash
ls -l /dev/ttyACM*
ls -l /dev/ttyUSB*
```

A ausência de um desses caminhos não significa necessariamente que a placa esteja defeituosa: o dispositivo pode não estar conectado, pode não ter enumerado corretamente ou pode utilizar outro caminho.

### Permissões seriais

Se houver erro de acesso, verifique as permissões do dispositivo. Por exemplo:

```bash
ls -l /dev/ttyACM0
```

Substitua o caminho pelo dispositivo encontrado no seu sistema.

No Fedora, pode ser necessário adicionar o usuário ao grupo `dialout`:

```bash
sudo usermod -aG dialout "$USER"
```

Depois, encerre e inicie uma nova sessão para que a associação ao grupo seja aplicada. Não é necessário alterar permissões de forma indiscriminada nem executar a aplicação como root por padrão.

## Uso

### Comandos disponíveis

```text
ibreakpoint
ibreakpoint --help
ibreakpoint --version
ibreakpoint about

ibreakpoint device list
ibreakpoint device info [DEVICE]

ibreakpoint doctor inspect [DEVICE]
ibreakpoint doctor check [DEVICE]

ibreakpoint analyze [DEVICE]
```

O argumento `DEVICE` representa o caminho da porta serial, quando aplicável. Também é possível definir o dispositivo por meio da variável de ambiente `IBP_DEVICE`:

```bash
IBP_DEVICE=/dev/ttyACM0 ./build/ibreakpoint analyze
```

A opção de cor pode ser controlada explicitamente:

```bash
./build/ibreakpoint --color=auto
./build/ibreakpoint --color=always
./build/ibreakpoint --color=never
```

O modo `auto` desativa as cores quando a saída padrão não é um terminal e respeita a variável `NO_COLOR`.

### Device não é o mesmo que firmware validado

O inventário inicial procura dispositivos seriais Linux em caminhos como:

- `/dev/serial/by-id/`
- `/dev/ttyACM*`
- `/dev/ttyUSB*`

Essa enumeração identifica candidatos a transporte. Ela **não comprova** que o firmware iBreakPoint está instalado ou que o dispositivo é compatível.

O módulo **DocTor Who** realiza a verificação do protocolo por handshake, conforme as operações implementadas no projeto.

## Protocolo e comunicação

A comunicação atual utiliza um protocolo textual ASCII sobre a conexão serial.

A especificação disponível está em [`docs/protocol.md`](docs/protocol.md).

O protocolo é experimental e voltado a um ambiente local de laboratório. Não deve ser considerado um canal autenticado ou seguro para ambientes hostis.

## Limitações conhecidas

- **Escopo:** esta versão prioriza enumeração serial, diagnóstico, análise de pré-requisitos e handshake.
- **USB:** a enumeração inicial utiliza nós seriais do Linux; descoberta detalhada por VID/PID via libusb e análise abrangente de descritores USB ainda não estão incluídas.
- **Firmware:** a compilação depende da instalação e configuração do Pico SDK.
- **Hardware:** testes automatizados não substituem a validação física em uma Raspberry Pi Pico.
- **Sistema:** o Analyze não instala pacotes nem altera automaticamente a configuração do host.
- **Protocolo:** o protocolo ASCII não possui autenticação e deve ser utilizado apenas no contexto previsto.
- **Autoria:** campos como `Created by` e `PwnBy` não devem ser interpretados como créditos confirmados enquanto permanecerem placeholders.

Essas limitações são parte do estado atual do projeto, não garantias de que funcionalidades futuras já estejam implementadas.

## Próximos passos

A evolução deve ocorrer de maneira incremental, mantendo cada funcionalidade verificável e documentada.

- [ ] Expandir a cobertura dos testes automatizados.
- [ ] Melhorar a identificação e a apresentação dos dispositivos.
- [ ] Documentar os casos de sucesso, falha e timeout do protocolo.

- [ ] Evoluir os diagnósticos sem confundir evidências observadas com inferências.

Os itens acima representam objetivos de desenvolvimento, não funcionalidades prometidas para a versão atual.
